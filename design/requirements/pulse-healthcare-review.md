# Design Review — Pulse Healthcare Design (Basic Healthcare Design)

This is a standalone feedback document, separate from the per-frame requirements docs (`landing-page.md`, `patient-dashboard.md`, `medical-records.md`, `settings-account.md`) in this same directory. It covers the whole file: the marketing landing page plus the three patient-portal screens (dashboard, health records, account settings).

**Source:** Figma file "Basic Healthcare Design" (fileKey `MtFODCLvM5tffZ2txAvdVL`), page "Page 1" (`0:1`), 4 top-level screens under frame `multi-canvas` (`8:9`): `screen-landing-page` (`8:10`), `screen-dashboard` (`8:198`), `screen-medical-records` (`24:190`), `screen-settings-account` (`24:353`).

## Overall impressions

The design reads as a coherent, competent, modern SaaS-style healthcare product — clean whitespace, a legible two-typeface system (Outfit for headings/numerals, Instrument Sans for body/UI), a consistent card language (soft gradient fill, two-layer shadow, teal accent), and marketing copy that leans into trust signals appropriate for healthcare (HIPAA mentions, patient counts, provider counts, star ratings, insurer logos). The portal screens (dashboard, records, settings) are especially strong: sensible information architecture, believable clinical data, and a calm, un-clinical visual tone that avoids feeling cold or bureaucratic.

That said, the file is a single desktop-only pass with no interaction states beyond "resting," no design tokens/variables defined in Figma at all, and — most importantly for a healthcare product — a recurring, systemic text-contrast problem with the brand teal and status-badge colors that would fail accessibility review if shipped as-is. None of this is a fundamental flaw in the design direction, but all of it needs to be resolved before engineering treats this as ship-ready.

## UX / usability concerns

- **Primary CTA color is reused for lower-priority "Learn more" links.** The rose `#f43f5e` is the primary action color (Join Pulse, Book Appointment, Save All Changes), but the same visual weight isn't given to the *actual* primary actions on the portal screens — "Save All Changes" is rose, matching marketing CTAs, while equally important actions like "Order Refill" and "Request Referral" use the teal brand color instead. There's no clear rule for when a button is teal vs. rose vs. white/bordered; recommend defining an explicit button-hierarchy system (primary/secondary/tertiary) before this scales past 4 screens.
- **FAQ accordion only shows one state.** Only the first of five FAQ items is expanded; there's no way to infer from the file whether this is single-open (accordion) or multi-open behavior, or what the expand/collapse transition should look like. Low risk, but worth a quick decision so builders don't guess.
- **The Account Settings form is ambiguous about edit mode.** Fields display real, pre-filled values in boxes that look almost, but not quite, like disabled inputs, alongside a separate "Edit Profile" button and a page-level "Discard Changes"/"Save All Changes" pair. It's unclear whether "Edit Profile" unlocks the three fields below it, or whether the fields are always editable and the page-level Save/Discard applies to the whole page (including notification toggles, devices, security). This ambiguity will produce inconsistent behavior if two engineers interpret it differently — worth nailing down with one flow diagram before build.
- **No feedback states anywhere.** Zero hover, focus, active, loading, error, empty, or success states exist across all four screens. For a product this content-rich (tables, toggles, forms, refill/sync actions), that's a lot of interaction design left to the implementer's judgment. This isn't unusual for a first design pass, but it means "requirements from Figma" alone cannot drive full implementation — flag this expectation with whoever is consuming the requirements docs downstream.
- **Icon reuse undermines scannability.** The "activity" (heartbeat/pulse) icon glyph is reused for the app logo, the Dashboard nav item, the Resting Heart Rate vital, the Blood Pressure vital, *and* both connected health devices (Withings watch, Apple Health). When the same glyph means "brand," "heart rate," "blood pressure," and "generic wearable device" in the same screen, it stops functioning as a recognition aid. Recommend a distinct icon per concept, especially for the two vitals and the device rows.
- **Footer is thin for a healthcare/insurance product.** No visible phone number, support email, physical business address, or crisis/emergency disclaimer ("if this is a medical emergency, call 911") anywhere in the footer or elsewhere on the marketing page. Healthcare sites conventionally carry this, and its absence is worth flagging as a content gap (see below) as much as a UX one.

## Accessibility concerns

This is the most significant category of feedback, both in count and in severity, given the healthcare context.

1. **Systemic text-contrast failures on the primary brand teal (`#0d9488`) used as text-on-white or text-on-light.** Computed against a white/near-white background, `#0d9488` yields roughly **3.7:1**, below the WCAG 2.1 AA minimum of 4.5:1 for normal-size text (the sizes it's used at — 14–15px — don't qualify for the lower 3:1 "large text" threshold). This color is used repeatedly and in high-visibility places:
   - The active "Home" nav link (landing header)
   - Every "Learn more" card link (services, benefit cards) — appears 7 times
   - The active tab underline/label ("Lab Results" tab)
   - Multiple card header links ("Schedule New," "View Full History," "Download PDF Report")
   
   The good news: the file already contains a working alternative. `#0f766e` is used elsewhere (the badge eyebrow text, the active sidebar nav label) for the same "interactive/emphasis" role and computes to roughly **5.5:1** against white — comfortably AA. **Recommendation: standardize on `#0f766e` (or darker) for any teal text on light backgrounds, and reserve `#0d9488` for backgrounds/fills only**, where its contrast against white foreground text is a separate (also-failing, see next point) question.

2. **Primary button contrast also fails.** White text on the primary teal (`#0d9488`) and primary rose (`#f43f5e`) button fills both compute to roughly **3.7:1** — below AA for the 15px semibold labels used ("Book Appointment," "Join Pulse," "Save All Changes," "Order Refill," "Subscribe"). This is the single most consequential finding in the review, since these are the site's core conversion actions. Recommend darkening both button fills by roughly one step (or moving to a heavier font weight/size that qualifies for the 3:1 large-text allowance, which is a much less robust fix) and re-testing.

3. **Status badges fail contrast most severely of all.** The green "Normal / Optimal / Stable / Active Refill Ready" badges (`#10b981` on `#ecfdf5`) compute to roughly **2.4:1** — badly below AA even for large text. The red "Flagged High" badge (`#f43f5e` on `#fff1f2`) computes to roughly **3.4:1**, also failing. These badges appear on every vital card, every prescription row, and every lab result row — they are the primary way the product communicates clinical status to a patient, which makes this the highest-priority fix in the entire file. A patient with even mild low-vision could plausibly misread "Flagged High" as unmarked/normal at these contrast levels. Recommend darkening both badge text colors substantially (e.g. toward `#047857`/`#0f766e`-family green and a deeper `#be123c`/`#9f1239`-family red) and re-verifying against the exact tint backgrounds used.

4. **Reliance on color for status, partially mitigated.** To the design's credit, every status badge pairs its color with distinct text ("Optimal" vs. "Flagged High," toggle knob position vs. just color), so meaning isn't conveyed by color *alone* — this is good practice and should be preserved in implementation, not lost. The one place this isn't true: the active/inactive nav link in the landing header has no non-color, non-weight indicator (no underline, no icon) — a minor version of the same issue.

5. **Small text sizing throughout the portal.** Status badges (11px), insurance card detail labels (11px), and several secondary metadata lines (12–13px) are quite small for a product whose user base skews toward people managing chronic conditions, some of whom are older patients or have low vision. Nothing here is a hard WCAG failure on size alone, but combined with the contrast issues above, this compounds real-world readability risk. Recommend revisiting the minimum type scale for a healthcare-specific audience.

6. **PHI/PII displayed unmasked with no privacy affordance.** The dashboard shows live vitals (heart rate, blood pressure, weight) and prescriptions; the settings screen shows full email, phone, physical address, and insurance member/group ID — all in plaintext, with no blur-on-inactivity, no "reveal" pattern, no auto-lock, and no visible session-timeout indicator, despite the product's own copy repeatedly claiming HIPAA compliance ("HIPAA-compliant digital secure health record," "HIPAA Compliant" badge, "HIPAA compliance setups"). This isn't a WCAG issue, but it's a healthcare-specific accessibility-adjacent trust concern worth raising with the product owner before implementation treats the static design as the full spec.

## Visual / brand consistency issues

- **Two teals doing the same job.** As covered above, `#0d9488` and `#0f766e` are both used for "interactive teal text," inconsistently, seemingly without a defined rule for which to use where. This is as much a design-system hygiene issue as an accessibility one — it suggests the file was built without a documented color token set (confirmed: `get_variable_defs` returns zero Figma variables for this file). Recommend formalizing a token set (e.g. `teal-600` for fills, `teal-700` for text-on-light) as part of turning this into a build-ready system.
- **No Figma variables/styles at all.** Every color, font size, and spacing value in this file is a raw, one-off value on individual layers rather than a shared style or variable. That's workable for a single-pass concept file, but it means nothing here is guaranteed consistent — e.g. it's worth spot-checking whether "body copy gray" is really `#475569` everywhere or drifts slightly between sections (the samples pulled for these requirements docs were consistent, but a full styles/variables audit wasn't exhaustively performed across every one of the ~400 text layers in the file).
- **Icon style mismatch via reuse**, covered under UX above — repeated use of the "activity" pulse-line glyph for unrelated concepts (brand mark, heart rate, blood pressure, generic device) is a visual-consistency issue as much as a usability one.
- **Card shadow/gradient treatment is applied very consistently** across service cards, benefit cards, step cards, review cards, stat cards, vital cards, and portal cards — this is a genuine strength and should be preserved as a formal "elevated card" component rather than re-derived per screen during implementation.

## Content gaps or unclear copy

- **No visible contact information** (phone, support email, physical office address, emergency-care disclaimer) anywhere on the marketing site — unusual and worth flagging for a healthcare provider's public site.
- **Footer "Legal Notice" is the only legal link** — no explicit "Privacy Policy" or "Terms of Service" link, which is a notable gap for a HIPAA-adjacent product that will be handling real health data.
- **Insurer/partner logos are styled text, not real logos** ("Aetna," "BlueCross," etc., rendered as plain bold type) — needs a decision on whether real brand marks are required (which raises licensing questions) or whether this text treatment is the final intended look.
- **"About S&A" footer link** — the label reads "About S&A," which looks like it may be a leftover/placeholder abbreviation rather than intentional copy (the product is named "Pulse Health" throughout, not "S&A"). Worth confirming with whoever owns the copy before treating it as final.
- **FAQ answers only exist for question 1 of 5** — items 2 through 5 ("Is Pulse Health HIPAA compliant?," "Can I message my care team directly?," "How do I request a prescription refill?," "Do you accept my insurance?") have no answer copy at all yet, despite being exactly the kind of high-value trust-building content a healthcare FAQ should prioritize.
- **Missing tab content on Health Records screen** — "Visit History," "Prescriptions," and "Immunizations" tabs exist in the UI but have no designed content behind them.

## Implementation blockers / complications

- **No responsive breakpoints exist anywhere in the file.** All four screens are single 1440px desktop artboards. Nothing here informs how the marketing nav collapses to mobile, how the portal's fixed 280px sidebar behaves below ~1024px, or how the 5-column lab-results table or multi-column form rows reflow. This should be treated as a hard blocker for mobile/tablet implementation, not something to improvise from the desktop layout alone.
- **No design tokens/variables in the Figma file**, and **no existing application code or design-token system in this repository yet** (the repo currently contains only the agent-pipeline scaffolding, no `src/`, no CSS, no component library). That means this design work will effectively originate the project's first token set — worth being deliberate about it (especially fixing the contrast issues above) rather than transcribing raw hex values 1:1 into code.
- **Ambiguous edit-mode behavior on the Settings form** (detailed in `settings-account.md`) could produce materially different implementations depending on which engineer builds it; resolve before assigning the work.
- **Undefined interaction/empty/error states across the board** mean the requirements docs in this folder describe structure and content faithfully, but cannot specify behavior that isn't in the file — implementers (or the delivery-lead agent) will need a follow-up round of lightweight interaction spec (even bullet points, not full mockups) before these screens are fully buildable without guessing.

## Summary of severity

If prioritizing fixes before implementation begins:
1. **Blocking / high severity:** primary-button and status-badge contrast failures (patient-safety-adjacent, since badges convey clinical status); undefined responsive behavior.
2. **Should-fix before build:** teal text-on-white contrast (`#0d9488` → `#0f766e`), settings edit-mode ambiguity, missing FAQ answers/tab content.
3. **Worth raising but not blocking:** icon reuse, missing footer contact/legal info, insurer-logo licensing question, "About S&A" copy check, lack of design tokens (acceptable to originate during implementation as long as it's done deliberately).
